# MADR-015 — Гибридный Server-Driven UI (SDUI)

**Статус:** Accepted (2026-06-07, владельцем) · **поправлен MADR-016** (2026-06-08)

> Формат тот же, что у MADR-001…014. Это сквозное решение: затрагивает и mobile
> (`plants-care-mobile`), и backend (`plants-care`), и слой оркестрации (`plant/CLAUDE.md`).
> Первая реализация — пилот экрана **home** (`GET /api/v1/ui/home`).
>
> ⚠️ **ПОПРАВКА (MADR-016).** Раздел «Контракт и версионирование» ниже описывает
> **типизированный** OpenAPI-словарь блоков (`Block` через `oneOf`+discriminator, кодген DTO).
> По итогам пилота владелец выбрал **опаковый Map-контракт + таблицу `ui_views` на backend**:
> ответ `GET /api/v1/ui/{screen}` — свободный объект (`blocks: array of object`), форма блоков
> описана **прозой** (этот ADR-словарь), а не типизированной схемой. Гибридный block-SDUI,
> граница «интерактив — нативно» и forward-compat **остаются в силе**. Где ниже сказано
> «типизированный `ui.yaml` / oneOf / кодген DTO блоков» — читать через MADR-016.

## Контекст

Два драйвера со стороны владельца:
1. **Менять UI без релиза** — состав/порядок/видимость блоков экрана, промо, сезонный контент
   катятся с сервера, не дожидаясь ревью сторов.
2. **Скорость доставки фич** — часть UI-поверхности должна меняться силами backend без
   мобильного релиза.

Текущая архитектура (Clean Architecture + Riverpod + кодген OpenAPI-клиента, MADR-001…014)
уже хорошо готова к этому: presentation подписан на провайдеры, данные приходят DTO,
ошибки/тема/сеть централизованы. Чего нет — слоя, где **сервер задаёт композицию экрана**.

Полный SDUI (сервер шлёт дерево примитивов `Column/Row/Text`, клиент — тупой интерпретатор)
для Flutter — плохая сделка: теряются типобезопасность, кодген, hot reload, нативный фил,
и обнуляется часть вложений в Clean Architecture. 34 экрана делятся на два класса:
read-heavy витрины (home, today, каталог, отчёт, ленты) и интерактивные флоу (мастер
добавления, sheet'ы ухода, auth, поиск, редакторы расписаний) — у вторых локальный state,
валидация, идемпотентность, модалки.

## Решение

**Гибридный block-SDUI.** Сервер собирает read-heavy экраны из **готовых нативных блоков**,
интерактивные флоу остаются полностью нативными.

- Сервер отдаёт не дерево виджетов, а **`ScreenLayout`** — список **блоков с данными**:
  `{ screenId, version, blocks: [{ type, data, action? }, …] }`.
- Клиент держит **`BlockRegistry`**: `Map<String type, Widget Function(BlockData, WidgetRef)>`,
  где значения — **обёртки над уже существующими виджетами** (`PlantCard`, `TodayCard`,
  `LocationChips`, …). Виджеты не выбрасываются и не переписываются — регистрируются.
- SDUI-ответ — это **обычный DTO** (кодген из OpenAPI, MADR-007), маппится в domain
  `List<Block>` руками (MADR-002). Riverpod / dio / `ApiError` / тема — без изменений.
- **Действия** описываются декларативно — `ActionDescriptor`
  (`{ kind, method, path, payloadTemplate }`). Клиент знает *как* исполнить (через
  существующий репозиторий/флоу), сервер говорит *что*. Идемпотентность care-events по
  `clientId` (MADR-006) **остаётся клиентской**.

### Граница (что НЕ через SDUI)

Интерактивные флоу остаются нативными **навсегда** в рамках этого решения:
мастер добавления (04), sheet'ы ухода (06), auth (07/09), унифицированный поиск (69),
редакторы расписаний/настроек (22/23/25/35). Признак «должно быть нативным»: локальный
многошаговый state, валидация форм, идемпотентные мутации, модальные sheet'ы.

### Контракт и версионирование (критично)

- **Словарь блоков — это контракт**, живёт в OpenAPI-спеке мобайла:
  `api/openapi/resources/ui.yaml` (`ScreenLayout`, `Block` через `oneOf`+discriminator,
  `ActionDescriptor`). За ним следит `contract-keeper`. Направление неизменно:
  **новый блок-тип сперва в спеке → бэкенд начинает его слать → клиент уже умеет рендерить.**
- **Forward-compatibility:** клиент шлёт версию каталога блоков (`X-UI-Catalog-Version`);
  сервер **не отдаёт** блок-типы выше неё. Неизвестный `type` клиент **скипает** без краша
  (graceful degradation, покрыто тестом). Старый клиент не ломается на новом блоке.
- **Никакой Turing-complete логики в JSON.** Блоки только параметризуются данными; вся
  логика — в нативных блоках. Желание «if/loop в JSON» = сигнал, что фича должна быть нативной.

## Причины

- Закрывает оба драйвера для витрин: композицию/порядок/видимость и сезонный контент сервер
  меняет без релиза; новый блок-тип катится contract-first.
- Минимальный риск: переиспользуем существующие виджеты, сеть, state, тему. Неизвестный блок
  деградирует мягко.
- Сохраняет нативный фил и типобезопасность там, где они важны (интерактив).

## Последствия

- Новый слой `lib/core/sdui/`: `BlockRegistry`, рендерер `ScreenLayout`, `ActionRunner`,
  `screenLayoutProvider` (шлёт `X-UI-Catalog-Version`).
- `api/openapi/resources/ui.yaml` + перегенерация клиента (`swagger_parser`).
- На стороне backend — эндпоинты композиции `GET /ui/<screen>` (поведение — источник правды
  backend), переиспользуют существующие сервисы данных, не дублируют логику.
- Read-heavy экраны постепенно переводятся на рендеринг из `ScreenLayout` вместо хардкода
  композиции. Интерактивные — не трогаются.
- **Каждый новый блок-тип** проходит: схема в `ui.yaml` (+ бамп версии каталога) → backend →
  регистрация в `BlockRegistry` → тест на маппинг и на graceful-degradation.

### Пилот (первая реализация)

Экран **home**: `GET /ui/home` отдаёт текущую композицию (`weather_strip` → `today_summary`
→ `location_chips` → `plant_grid`); `plant_grid` несёт `ActionDescriptor` «полить»
(`log_care` → существующий care-event флоу). Критерии успеха замеряются на пилоте:
(1) смена порядка/видимости блоков на сервере перестраивает клиент без релиза;
(2) стоимость добавления нового блок-типа end-to-end (в строках/времени);
(3) действие «полить» работает через `ActionDescriptor`, идемпотентность цела;
(4) старый клиент не падает на незнакомом блоке.

> **Отвергнутая альтернатива: полный SDUI (дерево примитивов).** Даёт максимум гибкости, но
> ценой типобезопасности, кодгена, нативного фила и вложений в Clean Architecture. Для набора
> экранов с богатым интерактивом — нерентабельно. Выбран гибрид; при необходимости отдельные
> блоки можно усложнять, не переходя на интерпретатор примитивов.
